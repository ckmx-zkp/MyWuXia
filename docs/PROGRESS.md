### 4 目标架构与统一执行链

| 层次 | 职责 | 实施约束 |
|---|---|---|
| 内容层 | 房间、NPC、物品、武学、对白和事件定义 | 静态配置与运行状态分离，稳定 ID、内容版本和引用校验；沿用 `src/content/` |
| 世界状态层 | 人物位置、关系、事实、任务阶段、游戏时间 | 先统一查询接口，再迁移存储；每项事实有确定来源，避免新旧字段长期双写 |
| 规则层 | 条件检查、成本、奖励、解锁 | 统一条件表达式与效果执行器；校验后原子结算，不在 UI 发奖励 |
| 事件层 | 显示对白、接受选择、等待战斗、恢复后继 | 主线、支线、门派、旅途共用执行契约，内容不同不产生新引擎 |
| 模拟层 | 生活产出、修炼消耗、战斗和时间推进 | 独立确定性结算，通过结构化结果接回事件 |
| 平台层 | 存储、音频、窗口、后台恢复 | 浏览器、PC、APP 共用内容和规则，以接口替换环境依赖 |

统一执行链：玩家行动 → 检查条件 → 执行规则 → 更新世界 → 记录经历 → 显示回响与后续入口。

- 继续以 `commands.js` 为命令入口，规则沿用 `src/game/`，UI 沿用 `src/features/`；只在职责确有需要时拆模块，不为了目录形式重写全部代码。
- 事件需保留事件 ID、节点 ID、选项 ID、待结算上下文及终局状态。战斗完成、失败、撤退必须回到相同事件上下文，不能二次随机或重复发奖。
- 统一条件支持 `all/any/not` 与明确的比较操作；可读取武学、身份、资源、关系、位置和事实。未知条件与效果应校验报错，不能静默放行。
- 效果通过受控接口修改资源、事实、关系、教学与道路资格；扣款、推进和奖励要么整体成功，要么不改变状态。
- 游戏随机源、时钟可注入；核心引擎不依赖 React、DOM、浏览器计时器或全局音频实例。

### 5 文案、剧情与世界回响契约

保留五模块：情境描摹、NPC 对白、交互抉择、判定回响、世界传闻。不要把参考作品只当作对白素材库，重点学习人物动机、信息揭露、选择代价与后果组织。

| 内容 | 下一步契约 |
|---|---|
| 出场条件 | 地点、人物状态、身份、前置事实；P0 建立组合条件底座 |
| 固定对白变体 | 根据关系、情报和任务结果选固定文本，明确优先级与默认回退 |
| 选项条件 | 分开定义是否显示与是否可选；不可选时说明缺少条件 |
| 后继 | 成功、失败、撤退、拒绝分别定义；允许汇合，持久事实不被汇合抹除 |
| 持续后果 | 改变交易、教学、人物位置、关系、道路和其他事件入口 |
| 创作记录 | 来源、改写说明、内容版本；具体字段随实施确定，不预先强制引入复杂编辑器 |

示例：护药的交涉与战斗路线可汇合到交付，但保存“交涉解决”“负伤护送”等事实，药商、师傅及后续事件读取事实产生不同回应。分支价值以持续后果判断，不能只换一句结算文字。

第一条贯通体验：生活获取材料 → 制药或筹钱 → 交药、交涉或战斗 → 人物关系变化 → 教学机会 → 修炼成长 → 下一处探索。其中制药属于后续生活深度，目前不能标为已实现。

- 持续劳动归并生活活动按时产出；护送等事件型循环通过节点和战斗结算。不能删掉计时后让重复点击无限领奖。
- 修炼、采药、劳动时间对应实际产出和消耗，保留活动计时、上限和离线结算。自动战斗计时用于回合推进和阅读，可另评估加速或即时结算。
- 现实时间与游戏时间分别建模。即时旅行或任务可扣除配置的游戏内时长；实施前明确命运期限、事件先后与每次时间推进入口，避免冻结命运、跳过事件或双重推进。
- 旧存档中的未完成行动需迁移为恰好一次的续接，不能直接丢弃或自动重复奖励。此节尚未实装。

### 7 分阶段集成顺序

| 阶段 | 范围 | 交付门槛 |
|---|---|---|
| P0-A 统一规则 | 世界事实查询、组合条件、统一效果；先提供旧数据适配 | 新支线不再增加专用判定代码，旧存档可继续游玩 |
| P0-B 统一事件 | 固定条件对白、后继、战斗续接、一次性结算；迁移护药与武当考核 | 多解法、失败恢复、条件回响和读档续接全部可验证 |
| P0-C 时间与平台接口 | 清除空等、整理循环收益与世界时间；隔离存储、音频、生命周期 | 不刷奖、不破坏命运，规则可脱离 React 测试 |
| P1 剧情贯通 | 八棵原著树和三帮命运逐步迁移；复杂事件调度、跨任务回响、记忆与 LLM | 成长改变剧情解法，剧情改变成长机会；模型故障不阻断流程 |
| P2 多端与扩展 | PC/APP 适配、同伴小队、更多区域门派、生活深度、多周目与按需云存档 | 同一规则和内容跨端复用，扩展通过既有契约接入 |

首批只选择《一车救命药》、武当考核、一条具有代表性的旧任务进行迁移验证。覆盖生活资源、师承成长、战斗续接与旧内容兼容后，再批量迁移；不一次性重写全部剧情。

- 先记录现有行为与存档样例，再建立查询适配和新契约；逐个入口切换，确认没有消费者后删除旧路径。
- 存档结构变化时升级版本，处理新旧事实冲突、内容版本变化与进行中事件。不能只做字段浅合并，也不把所有旧剧情强行标为完成。
- 内容校验检查稳定 ID、条件和效果类型、引用、后继、不可达节点、失败出口及结局可达性；图可达不等于条件可满足，仍需实际流程测试。
- 每批完成后遵循 `AGENTS.md` 第 10.1 节：测试与构建 → 部署 → 部署后测试 → 通过后提交并推送，报告实现边界与剩余工作。

### 8 P1 记忆、LLM 与叙事工具集成

- 后端可以接入 LLM API，用于丰富对白、传闻和回响；这提升叙事表现，不自动提升运行性能或玩法完整性，并会增加网络延迟和调用成本。
- 权威事实由规则引擎产生，记忆文档从结构化事实和经历生成，按角色、存档分支隔离，包含来源、版本与过时状态；最近 200 条日志不能替代长期摘要。
- 后端保管密钥，只传递当前 NPC 可知信息及允许表达的事实。模型输出限制为表现内容，不直接决定奖励、伤害、解锁、战斗结果或人物生死。
- 断网、超时、错误与不一致结果回退固定文案；缓存需绑定相关事实和内容版本，防止世界变化后复用过时回应。
- 首先选择单个事件对比固定版与增强版，验证一致性、延迟、缓存和费用，再扩大范围。LLM 不是 P0 完成条件。
- Ink/inkjs 仅在长剧情编写确有收益时试点；其叙事状态不能成为第二套权威世界状态，外部函数和标签须经统一规则接口执行。

### 9 多端方案

- 当前继续 React/Vite；PC 可比较 Tauri 与 Electron，APP 可评估 Capacitor。此为候选，不是已决定引入的依赖，不为封装提前重写 UI 或切换 Unity。
- 先抽取存储读写、音频播放、前后台切换和时间恢复接口，保留同一命令、内容与版本化存档模型；文件导入导出优先于账号和云同步。
- 后续评估安装包、离线内容缓存、自动更新、文件权限、音频策略和移动后台限制；各端恢复必须经过同一幂等结算入口，防止重复补算。
- 同伴与小队仍为玩法扩展优先项；平台封装按实际测试需要安排，云存档、排行和多人不作为个人单机体验的前置条件。

### 10 验收与现版本体验基线

框架验收：

1. 新增典型支线主要修改内容配置，无需增加专用引擎分支；不以强行零代码扩展作为所有新机制的要求。
2. 选择成本与效果原子结算，刷新、重复命令、战败、撤退、读档均不重复发奖；随机结果不会重掷。
3. 同一 NPC 根据实际经历显示不同固定对白，分支汇合仍保留事实；剧情结果改变至少一个实际玩法入口。
4. 生活 → 学艺 → 修炼 → 装备配招 → 战斗 → 恢复 → 后续机会可完整游玩，没有贫穷重伤死局。
5. 取消无交互等待后，循环收益、旅行遭遇、世界时间和命运期限仍正确；真实资源加载失败可恢复。
6. 旧存档、新角色、进行中活动和战斗有迁移与恢复覆盖，内容检查与真实路线测试同时通过。
7. 桌面与手机验证创角、移动、对白、活动、战报、存档和后台恢复；多端实施后补各平台同存档兼容验证。

|---|---|---|
| 创角和移动 | 出身、天赋、家传武学，临安房间移动 | 当前地点、对白和下一行动是否清楚 |
